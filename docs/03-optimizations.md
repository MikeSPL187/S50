# 03. Технические решения: оптимизации, их обоснование и границы

## 1. Принципы

1. Менять только то, что подтверждено чтением исходника **точной** сборки и что можно измерить.
2. Не менять KMI/ABI: ни раскладку структур, ни прототипы, ни набор/CRC экспортируемых символов
   (от `scheduler.ko`/`cpufreq_sugov_ext.ko` зависят проприетарные `scheduler_ext.ko`, `fpsgo.ko`).
3. Каждое изменение — отдельный патч с runtime-переключателем, чтобы A/B-сравнение шло **на одном образе**,
   а откат поведения не требовал перепрошивки.
4. Не трогать термозащиту, защиту батареи, лимиты частот, не фиксировать частоты на максимуме.
5. Не смешивать kernel-space и userspace: параметры PowerHAL/sysctl — отдельный каталог экспериментов (раздел 4).

## 2. Реализованные патчи (`kernel_device_modules-6.1`, файл `drivers/misc/mediatek/sched/sugov/cpufreq_sugov_main.c`)

Ветка `vienna-perf` поверх тега `MMI-W1UI36H.39-25-11-4`; патчи — [`patches/kernel_device_modules-6.1`](../patches/kernel_device_modules-6.1).
Затрагивают только `cpufreq_sugov_ext.ko`; `scheduler.ko` и `mtk_core_ctl.ko` не меняются.

### 0001 — `sugov_ext`: применять изменения лимитов до направленного rate limit

* **Проблема (факт из кода).** `sugov_update_next_freq()` сначала проверяет `sugov_up_down_rate_limit()`, и только
  потом смотрит на `sg_policy->need_freq_update`. Флаг выставляется (а) в `sugov_limits()` при изменении
  min/max политики — это freq_qos-запросы PowerHAL (`PERF_RES_CPUFREQ_MIN/MAX_CLUSTER_*`), FPSGO и thermal;
  (б) в `ignore_dl_rate_limit()` при росте DL-нагрузки. Комментарии самого кода требуют обходить rate limit в
  этих случаях, но направленный лимит их блокировал. Политика использует fast switch, поэтому новые лимиты
  применяются только при фиксации частоты — буст или термо-ограничение могли применяться с опозданием до
  `up/down_rate_limit_us`.
* **Метод.** Если `need_freq_update` установлен — пропустить направленную проверку. Остальная логика
  (расчёт частоты, принудительные обновления при смене WL/DSU) без изменений. Почему так: это минимальное
  изменение, восстанавливающее задокументированную в коде семантику; альтернативы (снижение rate limit
  глобально) меняют поведение для всех обновлений, а не только для смены лимитов.
* **Ожидаемый эффект — честно.** Проявляется, только когда rate limit больше интервала обновлений утилизации.
  Штатный PowerHAL держит 0 мкс в интерактивных сценариях и 10 мкс по умолчанию — **на штатных настройках
  эффект, вероятно, неизмерим**. Значимость определит диагностика (`04-cpufreq.txt`: фактические
  `up/down_rate_limit_us`). Ценность патча — корректность (в т. ч. своевременное применение термо-кэпа).
* **Переключатель.** `/sys/module/cpufreq_sugov_ext/parameters/rl_bypass_on_limits` (по умолчанию `Y`).
* **Проверка.** Perfetto: задержка между событием `power/cpu_frequency_limits` и следующим `power/cpu_frequency`
  при `up/down_rate_limit_us=10000`, `rl_bypass_on_limits=N` vs `Y`. Регресс-контроль: число переключений частоты
  (`stats/total_trans`), энергия на сценарий.
* **Откат.** `echo N > …/rl_bypass_on_limits` (root) или восстановление стокового `vendor_dlkm`.
* **Риск.** Минимальный: дополнительные переключения частоты возможны только при смене лимитов (их частота
  ограничена источниками лимитов).

### 0002 — `sugov_ext`: переключатель iowait-буста (по умолчанию — как в стоке)

* **Проблема (гипотеза, требует замера).** Унаследованный от schedutil iowait boost поднимает утилизацию при
  каждом пробуждении после I/O (удваивая до максимальной OPP при частых пробуждениях в пределах тика).
  На UFS это может поднимать частоту для фоновой I/O-работы, где CPU не узкое место; PowerHAL уже имеет
  отдельный ресурс `PERF_RES_IO_DATA_FS_BOOST`. Помогает ли буст отклику или тратит энергию на этом телефоне —
  неизвестно.
* **Метод.** Параметр модуля `iowait_boost_enable` (по умолчанию `Y` = стоковое поведение). При `N` состояние
  буста обнуляется и `sugov_iowait_apply()` ничего не добавляет.
* **Эффект по умолчанию — нулевой** (поведение идентично стоку). Это инструмент эксперимента, а не «оптимизация
  вслепую». Решение о смене значения по умолчанию — только по результатам A/B (время холодного запуска, I/O-тесты,
  энергия фоновой нагрузки, jank).
* **Переключатель.** `/sys/module/cpufreq_sugov_ext/parameters/iowait_boost_enable`.
* **Откат.** `echo Y > …` или перезагрузка (значение по умолчанию `Y`).

## 3. Изучено, но НЕ изменено (и почему)

| Наблюдение | Почему не патчим |
|---|---|
| `wl_cnt_cached` в `sugov_update_next_freq()` — один глобальный кэш на все кластеры: принудительное обновление после смены workload-типа EM получает только первый кластер | влияет лишь при `nr_wl_type > 1` (зависит от таблиц MT6878 в рантайме; `/proc/…` в диагностике); без подтверждения — только наблюдение |
| Adaptive margin / turn-point / group-aware DVFS MTK | сложные эвристики, настраиваемые PowerHAL; менять без трасс = гадание |
| `core_ctl` (парковка ядер) выключен по умолчанию | включение — решение userspace (PowerHAL); кандидат для эксперимента, а не патча |
| Ядро GKI (`boot.img`) | политика перехвачена vendor hooks; правка требует обхода protected exports, пересчёта `KERN_PROT_META`, меняет hash `boot` — риск без выгоды |
| Термо-модули, лимиты, батарея | запрещено задачей и здравым смыслом |
| zram / swappiness / LMKD / BFQ / read-ahead | userspace-конфигурация vendor; уже настроены MTK/Motorola (MGLRU, lz4, page-cluster 0); менять — только экспериментом с замерами |
| «Разгон», performance-governor, фиксация min-частот | противоречит цели энергоэффективности; не делается |

## 4. Каталог userspace-экспериментов (нужен root; НЕ часть ядра)

Каждый пункт — гипотеза; применять **по одному**, со стоковым контролем, по протоколу 05-profiling-and-test-plan.md.

| # | Параметр | Сток | Вариант | Ожидаемый компромисс |
|---|---|---|---|---|
| U1 | `/proc/sys/kernel/sched_pelt_multiplier` | 4 (полураспад 8 мс) | 2 (16 мс) | меньше скачков частоты и энергии на коротких всплесках ↔ медленнее разгон на касание |
| U2 | `sugov_ext/up_rate_limit_us`, `down_rate_limit_us` | по таблице PowerHAL 10 / 10 мкс (DefaultValue), 0 в интерактиве; фактическое значение — из диагностики | down 2000–5000 мкс | меньше «пилы» частоты ↔ дольше держится высокая частота; при U2 становится измеримым патч 0001 |
| U3 | `iowait_boost_enable` (патч 0002) | Y | N | энергия при фоновом I/O ↔ латентность I/O |
| U4 | `core_ctl` policy | выкл. | вкл. (PowerHAL-профиль MTK) | простой/лёгкая нагрузка ↔ задержка пробуждения ядер |
| U5 | zram `comp_algorithm` | lz4 | zstd | больше эффективная память ↔ CPU на (де)компрессию |

## 5. Что даст и чего не даст этот этап

* Даст: проверенную инфраструктуру, доказанно совместимый модуль с двумя изолированными изменениями, инструменты
  точного измерения и безопасный путь установки/отката.
* Не даст само по себе заметного прироста плавности/автономности на штатных настройках: стоковая конфигурация
  MTK/Motorola уже агрессивно настроена (PELT×4, FPSGO, uclamp-бусты, MGLRU). Реальные выигрыши, если они есть,
  будут найдены экспериментами раздела 4 и подтверждены замерами — и только после этого могут быть закреплены
  в ядре или vendor-конфигурации.
