# 05. Профилирование и план испытаний: сток против модифицированного модуля

> Ни одного замера на телефоне в этой сессии не выполнялось (доступа к устройству нет). Все числа в
> разделах «Результаты» — **ожидают исполнения**. Инструменты и протокол готовы.

## 1. Что измеряется без root и что требует root

| Метрика | Без root (adb shell) | Нужен root |
|---|---|---|
| Версия ядра, `vbmeta.digest`, свойства | `uname`, `getprop` | — |
| Частоты, governor, таблицы OPP, `time_in_state`, `total_trans` | чтение `/sys/devices/system/cpu/cpufreq/*` | запись тюнинга |
| cpuidle состояния/резидентность | чтение `/sys/devices/system/cpu/cpu*/cpuidle` | — |
| Параметры `sugov_ext` (rate limits), `/sys/module/*/parameters` | чтение (права 0644/0664) | изменение |
| Память, zram `mm_stat`, `/proc/pressure/*` (PSI) | обычно читаемо | — |
| Термозоны, батарея (`current_now`, `charge_counter`) | обычно читаемо | — |
| Время запуска приложений | `am start -W` | — |
| Кадры/jank | `dumpsys gfxinfo`, `SurfaceFlinger --timestats` | — |
| Трассы sched/freq/idle/gfx/power rails | `perfetto` (shell может писать в `/data/misc/perfetto-traces`) | расширенные события ftrace |
| Энергия | `dumpsys batterystats`, charge counter, power rails в Perfetto (если HAL отдаёт) | — |
| `/proc/modules` | зависит от SELinux | — |

## 2. Сценарии (scripts/device/10-baseline-profile.sh)

| # | Сценарий | Как | Метрики |
|---|---|---|---|
| 1 | Холодный и тёплый запуск | `am force-stop` → `am start -W -S`; затем HOME → `am start -W`, ×10 на приложение | TotalTime/WaitTime: медиана, p90 |
| 2 | Быстрая прокрутка | Настройки, 40 свайпов × 3 серии, `gfxinfo reset` перед серией | janky %, p50/p90/p95/p99 кадра, Missed Vsync, Slow UI thread, Deadline missed |
| 3 | Переключение приложений | циклическое `am start -W` по 5 приложениям ×10 | TotalTime |
| 4 | Лёгкая фоновая нагрузка | экран вкл., 30 мин типичного фона (синхронизация, музыка) | разряд по `charge_counter`, `time_in_state` |
| 5 | Длительная активность экрана | 30 мин прокрутки/видео (вручную, одинаковый контент) | разряд, температура, jank |
| 6 | Простой | экран выкл., 60 мин, **без USB** (adb по Wi-Fi или замер до/после) | разряд мкА·ч/ч, `suspend_resume` в Perfetto |
| 7 | Устойчивая нагрузка | `sustained`: 8 потоков shell × 10 мин, выборка 2 с | частота cpu7 во времени, макс. температуры зон, ток |
| — | Трасса | `perfetto` 20 с во время прокрутки | sched latency, freq residency, `cpu_frequency_limits`, frametimeline |

Условия (одинаково для обеих серий): фиксированная яркость (автояркость выкл.), 120 Гц как обычно, батарея 50–90 %,
телефон остыл ≥10 мин, комнатная температура записана, тот же Wi-Fi, 10 мин после загрузки, одинаковый набор
приложений. Каждая серия — минимум 3 повтора в разные дни/часы или чередование A-B-A-B.

## 3. Протокол A/B для патчей

Так как оба изменения имеют runtime-переключатели, для них **не нужно перепрошивать** между сериями:

1. Базовая линия: **стоковая прошивка** (до установки), сценарии 1–3, 7 + трасса → `profile-stock-*`.
2. После установки экспериментального `vendor_dlkm` с параметрами по умолчанию (`rl_bypass_on_limits=Y`,
   `iowait_boost_enable=Y`) → `profile-patched-default-*`. Ожидание: **нет измеримой разницы** со стоком
   (0002 по умолчанию идентичен стоку; 0001 почти не проявляется при 0–10 мкс). Это контроль регрессий.
3. Эксперименты (нужен root для переключения): U3 (`iowait_boost_enable=N`), U2+0001 и т. д. — по одному.
   Без root есть два возможных пути (оба требуют проверки): (а) вариант образа `vendor_dlkm` с файлом
   `lib/modules/modules.options` (`options cpufreq_sugov_ext iowait_boost_enable=0`) — libmodprobe читает этот
   файл (проверено по исходникам AOSP), но MTK грузит модули своим `init.insmod.sh`, и какой `modprobe` он вызывает,
   покажет `23-module-loading.txt` диагностики; переключение тогда требует перепрошивки `vendor_dlkm`;
   (б) параметры модуля в cmdline ядра (libmodprobe их тоже разбирает) через `fastboot oem config cmdl` —
   **не рекомендуется**: это изменение конфигурации загрузчика с неизученными последствиями ради тестов.
   Оба пути остаются гипотезами; вариант (а) не даёт переключения на лету — каждый вариант требует отдельной
   упаковки и перепрошивки `vendor_dlkm`, что повышает риск и затрудняет чистое сравнение. Практичнее: сначала
   базовая линия стока, затем решение о root (временном, через `init_boot`) для A/B на одном образе.
4. Анализ: `python3 tools/analyze_profile.py <A> <B>` — медианы, p90, U-тест Манна–Уитни; «значимо» только при
   p < 0,05 **и** |Δмедианы| ≥ 3 %.

## 4. Критерии принятия (что считается улучшением/регрессией)

| Метрика | Принять, если | Отклонить, если |
|---|---|---|
| Плавность | janky % и p95/p99 кадра не хуже стока (значимо) | значимый рост janky % или p99 |
| Отклик | время запуска/переключения не хуже стока | значимый рост медианы > 3 % |
| Энергия | разряд на сценарий ниже или равен | рост > 3 % при той же нагрузке |
| Температура | макс. температуры зон ≤ сток + 1 °C | выше без объяснения |
| Стабильность | 0 перезагрузок, 0 kernel warning/oops в `dmesg`/`logcat -b kernel` за 3 дня | любой panic/oops/зависание |
| Совместимость | все пункты раздела 5 работают | любая регрессия функции |

Если изменение улучшает одну метрику и ухудшает другую — это фиксируется в отчёте, и решение принимается
явно (по умолчанию — не включать).

## 5. Аппаратные функции (проверять после любой установки и после отката)

SIM/IMEI отображается (номер не публиковать), звонок, SMS, мобильные данные LTE/5G, Wi-Fi 2,4/5 ГГц, Bluetooth
(наушники), GPS-фикс, NFC, все камеры (фото/видео/переключение), вспышка, звук (динамики/микрофон/гарнитура),
датчики (автоповорот, приближение, отпечаток), вибрация, зарядка проводная (68 Вт), беспроводная, сон/пробуждение
(10 циклов), будильник из сна, OTA-приложение открывается.

**Важно:** Wi-Fi/BT/SIM нужно проверить ещё на стоке — после стирания `nvdata` в прошлой прошивке
эти функции не проверялись; иначе проблему ошибочно припишут ядру.
