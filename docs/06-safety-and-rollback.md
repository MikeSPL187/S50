# 06. Безопасность, резервирование, установка и откат

> Никакая команда, изменяющая память телефона, в этом проекте не выполнялась и не выполняется автоматически.
> Скрипты записи требуют явного аргумента `--i-understand` и ввода фразы подтверждения.
> Выполнять их можно только после вашего отдельного решения.

## 1. Что затрагивает экспериментальная установка

| Раздел | Меняется | Как |
|---|---|---|
| `vbmeta_a` | **да** | все стоковые дескрипторы сохранены побайтно; заменён только hashtree `vendor_dlkm`; rollback index 27, flags 0 (верификация **не** отключается); подпись — локальный ключ (OEM-ключ недоступен) |
| `vendor_dlkm_a` (логический, в `super`) | **да** | стоковый образ, в котором заменён один файл `lib/modules/cpufreq_sugov_ext.ko`; метки SELinux, владельцы, права всех 246 путей идентичны стоку; размер раздела не меняется (18 092 032) |
| `boot`, `init_boot`, `vendor_boot`, `dtbo`, `vbmeta_system`, `system_dlkm`, `system`, `vendor`, `product` | нет | — |
| GPT, preloader, lk, tee, nvdata, efuse(Backup), modem, debug_token, userdata, слот B | **никогда** | — |
| Загрузчик | не блокируется | блокировка на XT2409-5 с глобальной ROM опасна (CID 11 ≠ 50) |

## 2. Резервирование (до любых изменений)

Root нет, поэтому разделы нельзя прочитать с телефона (`fastboot fetch` в fastbootd запрещён на user-сборках —
проверено по исходникам AOSP `fastboot/device/commands.cpp`). Используется следующий путь:

1. `scripts/device/20-backup-stock.sh` копирует `boot`, `init_boot`, `vendor_boot`, `dtbo`, `vbmeta`, `vbmeta_system`
   из **того же пакета** и извлекает `vendor_dlkm_a`/`system_dlkm_a` из `super`. Эталон SHA-256 хранится
   **в репозитории** (`scripts/device/expected/W1UI36H.39-25-11-4.sha256`), а не в каталоге копии.
2. Затем скрипт сверяет копию с работающим телефоном (adb, без root). При разблокированном загрузчике (ORANGE)
   ошибка хэша `boot`/`vendor_boot` не останавливает загрузку, поэтому проверяется набор признаков — и
   **ни один из них, кроме первого, не является побайтным доказательством**:

   | Признак (без root) | Что устанавливает | Сила |
   |---|---|---|
   | `ro.boot.vbmeta.digest = 9935ea56…cc23` | `vbmeta_a`, `vbmeta_system_a` = пакет | криптографическое совпадение |
   | `/proc/version` = баннер ядра из `boot.img` пакета | работает ядро с той же строкой сборки и временем компиляции | сильный признак, не побайтное сравнение |
   | `ro.bootimage.build.date.utc = 1788995558` | рамдиск `init_boot` той же сборки | признак (метка времени), не побайтное сравнение |
   | `ro.boot.veritymode = enforcing` + загрузка | блоки verity-разделов, **прочитанные** при работе, совпали с корнями hashtree этого vbmeta | криптографически для прочитанных блоков; непрочитанные не проверены |
   | `ro.build.fingerprint`, `ro.carrier=teleu`, `ro.boot.flash.locked=0`, `vbmeta.device_state=unlocked`, слот `_a` | состояние системы и загрузчика | свойства |

   `vendor_boot_a` и `dtbo_a` не проверяются вовсе — их соответствие следует из журнала прошивки 30.10.2026
   (OKAY, MD5 совпали). Экспериментальная установка эти разделы не меняет.
3. **Маркер `DEVICE-MATCH.txt`** создаётся только при полном успехе сверки; любой прежний маркер удаляется в
   начале каждого запуска (в том числе если adb недоступен). Маркер содержит проверенные значения, время
   создания, хэш эталона и хэш `SHA256SUMS` копии. Перед прошивкой сверку нужно повторить:
   `bash 20-backup-stock.sh --recheck-only` — предполётная проверка принимает маркер не старше 120 минут
   (`MATCH_MAX_AGE_MIN`).
4. Хранить копию минимум в двух местах (Steam Deck + внешний носитель); полный 7z-пакет тоже сохранить.

## 3. Предполётная проверка (только чтение)

`scripts/device/30-preflash-gate.sh <артефакт>` (в режиме загрузчика). Политика: всё, что важно для
безопасности, — **СТОП**; нечитаемый параметр — тоже СТОП, кроме двух явно оговорённых случаев.

| Группа | Условия допуска (иначе СТОП) |
|---|---|
| Артефакт | SHA256SUMS; валидный hashtree; vbmeta отличается от стока только дескриптором `vendor_dlkm`, rollback index/flags как в стоке; корневой дайджест vbmeta = футер образа; **размер образа = 18 092 032** (размер стокового логического раздела: разметка `super` не меняется) |
| Резервная копия | совпадает с эталоном из репозитория |
| Маркер сверки | существует; формат 1; возраст ≤ 120 мин; та же сборка; стоковые vbmeta.digest, строка ядра, метка init_boot; veritymode=enforcing; слот `_a`; разблокировка; `teleu`; привязан к текущему эталону и к этой копии |
| fastboot | одно устройство; `vienna`, `XT2409-5`, CID `0x000B`, `ro.carrier=teleu`; загрузчик (не fastbootd); `current-slot=a`; `slot-successful:_a=yes`; `slot-unbootable:_a=no`; `has-slot:vbmeta=yes`; `snapshot-update-status=none`; `version-bootloader` содержит `W1UI36H.39-25-11-4` |
| Оговорки | `getvar ro.build.fingerprint`: если отвечает — должен совпасть, если не поддерживается — информационно. `securestate`: `*unlock*` — OK, `*lock*` — СТОП, пусто — допускается только потому, что разблокировка уже подтверждена обязательным свежим маркером |

## 4. Процедура экспериментальной установки (выполняет только пользователь)

```
bash scripts/device/20-backup-stock.sh --recheck-only      # в Android, непосредственно перед прошивкой
adb reboot bootloader
bash scripts/device/30-preflash-gate.sh ~/moto-kernel/out/artifact
bash scripts/device/40-flash-experimental-vendor-dlkm.sh ~/moto-kernel/out/artifact --i-understand
```

Порядок внутри скрипта и почему он такой:

1. `fastboot flash vbmeta_a` (загрузчик). Если сбой — `vendor_dlkm` ещё стоковый; вернуть стоковый vbmeta.
2. `fastboot reboot fastboot` → fastbootd (recovery-рамдиск из `vendor_boot`, **не зависит** от `vendor_dlkm`);
   проверка `current-slot=a`.
3. `fastboot flash vendor_dlkm_a`.
4. `fastboot reboot bootloader` — **система не загружается автоматически.** Скрипт показывает состояние слотов;
   в этот момент ещё можно вернуть сток (`90-restore-stock.sh`), не загружая модифицированную систему.
5. Загрузка системы — только после отдельного ввода `BOOT`.

`fastboot boot` не используется (сторонний отчёт: отсутствует на vienna; не проверено на XT2409-5).
`boot` не прошивается, поэтому сторонне описанная «предварительная проверка boot по vbmeta» не затрагивается.

## 5. Откат

Из загрузчика (Питание + Громкость вниз), из fastbootd или из работающего Android:

```
bash scripts/device/90-restore-stock.sh --i-understand                 # vbmeta_a + vendor_dlkm_a
bash scripts/device/90-restore-stock.sh --i-understand --all           # + boot/init_boot/vendor_boot/dtbo/vbmeta_system/system_dlkm (слот A)
bash scripts/device/90-restore-stock.sh --i-understand --set-active-a  # если загрузчик сам переключился на слот B
```

**Слот B не является запасным.** После прошивки 30.10 разделы `*_b` загрузочной цепочки остались от Android 15,
а в `super` у слота B нет `vendor_b`, `vendor_dlkm_b`, `product_b`, `system_ext_b` (размер 0). Если
модифицированный слот A не загрузится 7 раз подряд, загрузчик может переключиться на B — Android 16 с B не
запустится, телефон останется в загрузчике.

**Откат выполняется только при известном состоянии телефона.** Источники уверенности:

| Ситуация | Что проверяется | Решение |
|---|---|---|
| Android работает (adb) | fingerprint `W1UI36H.39-25-11-4`, слот `_a`, `vbmeta.digest` = стоковый или экспериментальный из журнала | иначе — **запрет без обхода** |
| Android не работает, слот A | `version-bootloader` этой сборки + журнал `EXPERIMENT-STATE.txt` с неоткатанным экспериментом | без журнала или при нечитаемой версии — только с `--accept-unverified-state`; чужая сборка — запрет |
| Слот B активен | `--set-active-a`; `slot-successful:_b ≠ yes`; загрузчик `V1UI35H.11-39-16` или `W1UI36H.39-25-11-4`; журнал | `slot-successful:_b=yes` означает рабочую систему на B (например, после OTA) — **запрет без обхода** |

Журнал `EXPERIMENT-STATE.txt` ведёт `40-flash-experimental-vendor-dlkm.sh`: до первой записи — хэши артефакта,
ожидаемый `vbmeta.digest` экспериментального состояния, версия загрузчика, слот; затем — каждый записанный
раздел. `90` добавляет событие `restored`. Ограничение: `version-bootloader` подтверждает сборку загрузчика,
а не каждого раздела; поэтому он используется только вместе с журналом или adb-сверкой.

Проверки модели и CID делаются **только в загрузчике**: в AOSP fastbootd переменных `sku`, `cid`,
`slot-retry-count` нет (проверено по `fastboot/constants.h`). Запущенный из fastbootd, скрипт сначала
перезагружает телефон в загрузчик (это не запись).

Порядок записи: `vbmeta_a` (+ `--all`) в загрузчике → при необходимости `--set-active=a` (до входа в fastbootd,
чтобы recovery запустился из стокового A) → fastbootd → `vendor_dlkm_a` → возврат в загрузчик → загрузка системы
только после ввода `BOOT`.

После отката `00-readonly-diagnostics.sh` должен показать совпадение признаков из раздела 2.

Если fastbootd недоступен: стоковый `vbmeta_a` всё равно восстанавливается из загрузчика; для `vendor_dlkm_a`
последний резерв — сервисная прошивка `servicefile.xml` (не стирает userdata), **но** она снова пишет GPT и
preloader и стирает `nvdata`; применять только осознанно, через проверенный ранее guarded runner, адаптированный
под слот A. Полная прошивка `flashfile.xml` стирает данные.

## 6. Влияние на OTA

* `vendor_dlkm_a` изменён → при инкрементальном OTA `update_engine` проверит хэш исходного раздела и **откажется**
  ставить обновление (телефон не повредится, OTA просто не установится).
* Перед OTA: `90-restore-stock.sh`, загрузиться, убедиться в стоковом `vbmeta.digest`, затем обновляться.
* После OTA сборка изменится: артефакт для `W1UI36H.39-25-11-4` **нельзя** ставить на новую сборку — нужен новый тег
  Motorola и повторный прогон конвейера (все гейты привязаны к конкретной сборке).
* Разблокированный загрузчик уже даёт состояние «orange» и непрохождение строгой аттестации; смена ключа vbmeta
  этого не меняет, но меняет `vbmeta.digest` (видно в аттестации).

## 7. Основные риски и меры

| Риск | Вероятность / последствие | Мера |
|---|---|---|
| Загрузчик не принимает vbmeta с чужим ключом | низкая (libavb, unlocked) / запись отклонена, ничего не изменено | скрипт останавливается до записи `vendor_dlkm` |
| fastbootd не поддерживает запись `vendor_dlkm_a` | низкая / запись отклонена | восстановить стоковый `vbmeta_a` |
| Ошибка в модуле → нет загрузки | низкая (код = сток + 2 изолированных изменения, KMI-gate пройден) / bootloop | откат из загрузчика + fastbootd |
| После 7 неудачных загрузок загрузчик переключается на непригодный слот B | возможна при bootloop / телефон в загрузчике | `90-restore-stock.sh --set-active-a` |
| Аварийный путь (fastbootd, приём vbmeta с чужим ключом) не проверен на этом телефоне | неизвестна / может потребоваться сервисная прошивка | проверено только на имитаторе; первая установка — при полностью заряженном телефоне и готовом пакете прошивки |
| Неверные метки SELinux в `vendor_dlkm` | исключено проверкой файл-в-файл | `make-vendor-dlkm.sh` прерывается при любом расхождении |
| OTA не ставится | высокая при модификации / неудобство | откат перед OTA |
| Перегрев/потеря термозащиты | не затрагивается | термо-модули и лимиты не менялись |
